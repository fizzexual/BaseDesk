# BaseDesk v0.2 — Support → Revenue

**Date:** 2026-07-12
**Status:** Approved for implementation
**Repo:** https://github.com/fizzexual/BaseDesk
**Depends on:** v0.1 (shipped) — data layer, store, UI primitives, icon set, reports charts.

---

## 1. Why this exists

BaseDesk's differentiation strategy is a four-pillar roadmap that reframes "helpdesk" into something incumbents structurally can't match: **Support → Revenue** (this spec), **Transparency portal**, **Slack-native support**, and **Proactive/AI support**, built in that order. Each ships as its own spec → plan → implementation cycle.

Pillar #1 is first because it fits the existing data model with no new infrastructure, is fully demoable self-hosted, and is the most category-redefining: it turns support from a cost center into a growth channel. Zendesk/Freshdesk/Intercom treat support and revenue as separate systems (helpdesk vs. Salesforce), forcing agents to leave the conversation to capture money. BaseDesk captures it in-place. The v0.1 reference UI already teased this with a "$12.50k Sales closed" pill.

Three money motions the research surfaced — **expansion/upsell**, **retention/saves**, and **inbound conversion** — plus **account health** are not four features. They are four flavors of one object (a `Deal` with a `type`) plus one rollup (deals grouped per company). That keeps this to a single coherent spec.

## 2. Scope

### In scope (v0.2)

1. **`Deal` object** — first-class entity linked to a contact and (optionally) the originating ticket.
2. **Revenue in the conversation** — a Revenue block in the ticket context panel: view linked deals, log a new opportunity, change stage.
3. **Revenue section** (`/revenue`) — two tabs: **Pipeline** (summary cards + filterable deal table) and **Accounts** (company-level health table).
4. **Live money pill** — the Topbar pill shows deals won in the last 7 days ("$12.5k closed this week"); "resolved this week" moves to Reports.
5. **Revenue reporting** — won-over-time area chart, by-type donut, win-rate and saved-revenue stat cards, reusing v0.1 chart components.
6. **`mrr` on Contact** — one nullable field (current monthly spend, cents) to weight account health.
7. **Seed** — ~35 deterministic deals + `mrr` on company contacts.
8. **Tests** — server (deal CRUD, stage transitions, revenue stats, bootstrap) + web store (optimistic flows, account-health rollup, pill math).

### Out of scope (future, noted not built)

Company as a first-class entity (group by existing `company` string instead), multi-currency, kanban drag-and-drop, activities/tasks, sales quotas/forecasting, per-deal line items.

## 3. Data model

New entity (mirrored `server/src/types.ts` ↔ `web/src/data/types.ts`):

```ts
export type DealType = 'expansion' | 'retention' | 'inbound';
export type DealStage = 'open' | 'won' | 'lost';

export interface Deal {
  id: string;              // 'd_' + 8 hex
  title: string;
  type: DealType;
  stage: DealStage;
  value: number;           // integer cents (>= 0)
  currency: string;        // 'USD' in v0.2
  contactId: string;       // required
  ticketId: string | null; // optional link to originating conversation
  ownerId: string;         // agentId
  note: string;
  createdAt: string;       // ISO
  closedAt: string | null; // set when stage -> won|lost, cleared when -> open
  updatedAt: string;       // ISO
}
```

Change to existing model: `Contact` gains `mrr: number | null` (integer cents, current monthly recurring spend). Nullable — individuals/consumers have `null`; company contacts carry a value.

**Derived: account health** (computed, never stored) — grouped by `Contact.company` string (contacts with `company === null` are excluded from Accounts):

```ts
export interface AccountHealth {
  company: string;
  contactIds: string[];
  mrr: number;              // sum of contact mrr in the company (cents)
  openTickets: number;      // inbox, non-closed, non-snoozed tickets for these contacts
  urgentOpen: number;       // of those, priority urgent|high
  wonValue: number;         // sum of won deal value (cents)
  openPipeline: number;     // sum of open deal value (cents)
  openExpansion: number;    // count of open deals type=expansion
  openRetention: number;    // count of open deals type=retention
  status: 'at_risk' | 'expansion_ready' | 'healthy';
}
```

Health classification (evaluated in order): **at_risk** if `openRetention > 0` OR `urgentOpen >= 1`; else **expansion_ready** if `openExpansion > 0`; else **healthy**.

## 4. Revenue aggregates (extends `StatsOverview`)

Add to the stats payload (server `computeStats` + local mirror), all cents unless noted:

```ts
revenue: {
  wonLast7Days: number;                 // sum value where stage=won and closedAt within 7d
  wonThisMonth: number;                 // calendar-month-to-date won
  openPipeline: number;                 // sum value where stage=open
  savedRevenue: number;                 // sum value where stage=won and type=retention (this month)
  winRate: number;                      // won / (won + lost), 0..1, closed deals all-time; 0 if none
  wonByType: Record<DealType, number>;  // won value per type, calendar-month-to-date (matches wonThisMonth window)
  wonLast14Days: { date: string; count: number; value: number }[]; // per-day won, for the area chart
}
```

The Topbar pill reads `revenue.wonLast7Days`.

## 5. REST API (server)

| Method/Path | Body | Returns / behavior |
|---|---|---|
| GET `/api/bootstrap` | — | `BootstrapData` now includes `deals: Deal[]` |
| GET `/api/deals?stage=&type=&contactId=` | — | `Deal[]`, newest `updatedAt` first |
| POST `/api/deals` | `{title, type, value, contactId, ticketId?, ownerId?, note?}` | `Deal` — stage defaults `open`; `ownerId` defaults to currentAgent; `closedAt` null; id `d_`+8hex; validates contactId exists, value >= 0, type valid → else 400 `{error}` |
| PATCH `/api/deals/:id` | `Partial<{title, type, stage, value, ownerId, note}>` | `Deal` — setting `stage` to `won`/`lost` sets `closedAt = now` (if not already closed); setting back to `open` clears `closedAt`; bumps `updatedAt`; unknown id → 404 `{error}`; invalid stage/type/value → 400 |
| DELETE `/api/deals/:id` | — | `{ok:true}` — hard delete (deals are internal annotations, not customer messages; the no-hard-delete rule still protects tickets/contacts); unknown id → 404 |
| GET `/api/stats` | — | `StatsOverview` extended with the `revenue` block above |

Account health is computed **client-side** in the store (all tickets, contacts, and deals are already resident) — no `/api/accounts` endpoint in v0.2.

## 6. Web data layer

- `types.ts`: add `Deal`, `DealType`, `DealStage`, `AccountHealth`; add `mrr` to `Contact`; extend `BootstrapData` with `deals`; extend `StatsOverview` with `revenue`.
- `repository.ts`: add `listDeals(filter?)`, `createDeal(input)`, `updateDeal(id, patch)`, `deleteDeal(id)`.
- `api.ts` (ApiRepository) + `local.ts` (LocalRepository): implement the above with identical semantics (stage→closedAt, defaults, validation). LocalRepository persists deals in the same `basedesk-data-v1` blob and seeds from `shared/seed.json`.
- `store.ts`: add `deals: Record<string, Deal>`; hydrate from bootstrap; actions `createDeal`, `updateDeal` (optimistic + rollback, same pattern as `patchTicket`), `deleteDeal` (optimistic remove + rollback); selectors `dealsForTicket(id)`, `dealsForContact(id)`, `accounts()` (AccountHealth[] grouped by company), `revenueForCompany`.
- `hooks.ts`: `useDealsForContact`, `useAccounts`, `useRevenueStats` (memoized like `useCounts`).
- `money.ts` (new util): `formatMoney(cents, {compact?})` → `$12.5k` / `$1,200`; `parseMoney(str)` for the deal input.

## 8. Money handling

Values are integer **cents** everywhere (DB, API, store) — no floats. `formatMoney` renders compact for pills/cards (`$12.5k`) and grouped for tables (`$1,200`). `parseMoney("1,200.50")` → `120050`. Single currency (USD) in v0.2; the `currency` field is carried but not surfaced in UI.

## 9. Error handling

- Optimistic create/update/delete with snapshot rollback + error toast (identical to v0.1 ticket mutations).
- API validation returns `{error}` with 400/404; the client surfaces a toast and rolls back.
- Deleting a deal is confirmed in the dialog; toast confirms (no undo in v0.2 — deals are cheap to recreate; noted as a future nicety).
- Corrupt localStorage in demo mode reseeds (existing v0.1 behavior covers deals via the same blob).

## 10. Testing & verification

- **Server** (`server/test/`): deal create defaults + validation; PATCH stage→closedAt set/clear; DELETE + 404; bootstrap includes deals; `revenue` stats correctness (wonLast7Days windowing, winRate with zero-closed guard, savedRevenue = won retention, wonByType sums).
- **Web store** (`web/test/`): createDeal/updateDeal optimistic + rollback on repo failure; deleteDeal; `accounts()` grouping + health classification (at_risk precedence over expansion_ready); won-this-week selector; parity of LocalRepository deal semantics with the server.
- **Type gate:** `tsc --noEmit` clean both workspaces, strict.
- **Manual:** log a deal from a ticket → appears in Pipeline and in the contact's account; mark won → pill and reports update; Accounts health badges reflect deals/tickets; both themes; contrast on the three health badge colors.

## 11. Architecture notes / isolation

The `Deal` object and its aggregates are a self-contained slice: the server routes, the repository methods, the store slice, and the `revenue/` feature directory can each be understood and tested independently. The only touches to existing files are additive (a field on Contact, a block in ContextPanel, a band in Reports, the Topbar pill, one rail/sidebar/palette nav entry, a possible single-series prop on AreaChart). No existing behavior changes.

## 12. Success criteria

- A deal can be logged from a conversation and flows to Pipeline, Accounts, Reports, and the money pill, persisted across restarts through the real server + SQLite.
- All three motions (expansion, retention, inbound) and account health work from the one object.
- The money pill shows real won-this-week revenue matching the reference screenshot's intent.
- No third-party CRM/chart/icon dependency added; strict TS clean; server + web tests green.
- Ships as its own set of readable commits and is pushed to GitHub.
