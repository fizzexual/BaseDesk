# BaseDesk v0.4 — AI Agents, Channels, and Settings upgrades

**Date:** 2026-07-12
**Status:** Approved for implementation (build order: AI Agents → Channels → Settings)
**Depends on:** v0.1–v0.3 (shipped). Reuses the rule-based AI engine (`web/src/features/ai/engine.ts`), the ticket/contact model, SQLite storage, the `app_settings` table, and the design system.

## Pillar A — AI Agents (autonomous layer)

### Concept
An **AI Agent** is a configurable bot that processes tickets as they arrive, at an escalating autonomy level, always human-in-the-loop. It reuses the rule-based engine (draft/triage/summarize) plus a new KB **deflection** matcher.

### Data model
```ts
type Autonomy = 'suggest' | 'draft' | 'resolve';
interface AiAgent {
  id: string; name: string; avatarHue: number; enabled: boolean;
  autonomy: Autonomy;
  scopeTags: string[];          // empty = any tag
  scopePriorities: TicketPriority[]; // empty = any priority
  createdAt: string;
}
type AiActionKind = 'triage' | 'draft' | 'resolve';
type AiActionStatus = 'pending' | 'approved' | 'dismissed' | 'sent';
interface AiAction {
  id: string; agentId: string; ticketId: string;
  kind: AiActionKind; status: AiActionStatus;
  draftBody: string | null;
  suggestedPriority: TicketPriority | null;
  suggestedTags: string[];
  kbArticleId: string | null;   // the article a resolve/deflect cited
  createdAt: string; resolvedAt: string | null;
}
```

### Engine additions (`features/ai/engine.ts`)
- `deflect(text, kb): { articleId: string; score: number } | null` — scores the ticket text against KB article title+body term overlap; returns the best match when the score clears a confidence threshold.
- `runAgent(agent, ctx): AiAction | null` — pure decision function. `ctx = { subject, bodyText, contactName, agentName, currentPriority, currentTags, canned, kb }`. Returns:
  - autonomy `suggest` → a `triage` action with suggested priority/tags (or null if nothing to suggest).
  - autonomy `draft` → a `draft` action carrying `draftReply(...)` output.
  - autonomy `resolve` → if `deflect` hits, a `resolve` action citing the article (its reply = a short answer + the article body); else falls back to a `draft` action.
  - Respects `scopeTags`/`scopePriorities` (skips non-matching tickets → returns null).

### Where agents run
- **On ticket create** (server `POST /api/tickets` and any channel inbound): `runAgents(db, ticket, firstBody)` picks the highest-autonomy enabled matching agent, records its `AiAction`. For `resolve` actions the server also sends the reply (an agent message) and sets the ticket `status = solved`.
- **On demand**: `POST /api/ai/run` processes current open, unactioned inbox tickets (so the queues fill without waiting). The UI exposes this as "Run agents now".
- Seed ships 2 agents (one draft-level "Reply Assistant", one resolve-level "Deflection Bot") and ~10 seeded actions across the two queues.

### REST
| Method/Path | Body | Returns |
|---|---|---|
| bootstrap | — | adds `aiAgents: AiAgent[]`, `aiActions: AiAction[]` |
| POST `/api/ai/agents` | `{name, autonomy, scopeTags?, scopePriorities?}` | `AiAgent` |
| PATCH `/api/ai/agents/:id` | `Partial<{name,enabled,autonomy,scopeTags,scopePriorities}>` | `AiAgent` |
| DELETE `/api/ai/agents/:id` | — | `{ok:true}` |

### UI (wire the existing sidebar "AI Agents" group)
- **Overview** (`/ai`) — keep the copilot intro; add a fleet panel: agent cards (name, enabled toggle, autonomy pill, scope, stats: drafted / resolved / pending) + "New agent" + "Run agents now".
- **Agent editor** — dialog: name, enabled, autonomy segmented (Suggest/Draft/Resolve), scope (tag chips + priority multiselect), delete.
- **Drafts** (`/ai/drafts`) — approval queue of `kind=draft, status=pending` actions: each row shows the ticket + requester + the prepared draft (editable inline), Approve (sends) / Dismiss. Live count in the sidebar.
- **Resolved by AI** (`/ai/resolved`) — tickets resolved via a `resolve` action, with the cited KB article. Live count.
- Sidebar "AI Agent" group counts reflect pending drafts and resolved totals.

## Pillar B — Channels (real multi-channel pipeline)

### Concept
A **Channel** is a connected source of tickets. Inbound arrives via a generic authenticated webhook or the live web-chat widget; tickets carry their channel and show a source badge.

### Data model
```ts
type ChannelType = 'webchat' | 'webhook' | 'email' | 'discord' | 'slack' | 'whatsapp';
interface Channel {
  id: string; type: ChannelType; name: string; enabled: boolean;
  inboundToken: string;         // authenticates POSTs to this channel's inbound URL
  address: string | null;       // forwarding address / handle shown in the UI
  createdAt: string;
}
```
`Ticket` gains `channelId: string | null`.

### Real, working (no external infra)
- **Inbound webhook** — `POST /api/channels/:id/inbound?token=…` with `{ from: {name, email}, subject?, body }`: validates the token, finds/creates the contact by email, opens a ticket with `channelId` set and `channel` mapped from the channel type, then runs AI agents on it. A real Discord/Slack/email forwarder points here.
- **Web chat widget** — a standalone page served at `/widget.html` (static, in `web/public`) that: starts a conversation (POST inbound to the seeded webchat channel), then polls `GET /api/channels/:id/thread?token=&contact=` for agent replies and renders them. "Copy embed code" in the UI gives a `<script>`/iframe snippet. Fully functional end-to-end within one deploy.
- **Channels UI** (`/channels`, new rail icon) — a directory of channel types with Connect → config; connected channels show status, the inbound URL + token, and ticket counts; a "Web chat" card with a live widget preview + embed code. Per-ticket **source badge** (channel icon + name) in the ticket header and optionally the inbox.

### The honest edge (labeled in-UI)
Native live Discord-bot / IMAP-mailbox connectors and outbound email/Discord delivery need a hosted, networked backend. Those channel types are configurable (name, address, inbound token) and their cards say "Inbound works via forwarding/webhook now — native connector and outbound delivery arrive in a hosted deploy." Webchat + webhook are fully live today.

### REST
| Method/Path | Body | Returns |
|---|---|---|
| bootstrap | — | adds `channels: Channel[]` |
| POST `/api/channels` | `{type, name, address?}` | `Channel` (generates `inboundToken`) |
| PATCH `/api/channels/:id` | `Partial<{name,enabled,address}>` | `Channel` |
| DELETE `/api/channels/:id` | — | `{ok:true}` |
| POST `/api/channels/:id/inbound?token=` | `{from,subject?,body}` | `{ticketId}` (public, token-gated) |
| GET `/api/channels/:id/thread?token=&contact=` | — | `Message[]` (public, for the widget) |

Seed: 2 channels (a `webchat` "Website" and an `email` "support@" forwarding), and assign existing tickets' `channelId` where their `channel` type matches.

## Pillar C — Settings upgrades

### C1. Team & invites (new `/settings/team`)
`Agent` gains `status: 'active' | 'invited'` and `inviteToken: string | null`.
- Team tab lists members (avatar, name, email, role admin/agent, status). "Invite teammate" dialog: name + email + role → `POST /api/agents` creates an `invited` agent with a generated `inviteToken`; the UI shows a copyable invite link (`/join?token=…`). Change role, remove member. Honest note: real email delivery of invites needs SMTP (hosted); the link is shareable now.
- REST: `POST /api/agents {name,email,role}`, `PATCH /api/agents/:id {name?,role?}`, `DELETE /api/agents/:id`. bootstrap already returns agents (now with status/inviteToken).

### C2. Richer profile
`Agent` gains `signature: string`. Profile tab: edit display name, a reply **signature** (appended context for drafts), avatar hue picker, role chip. Saved via `PATCH /api/agents/:id` for the current agent. The composer/AI draft use the signature as the sign-off when present.

### C3. Better SLA — business hours
`app_settings` key `sla_hours` = `{ enabled: boolean, timezone: string, days: number[], start: string /*HH:MM*/, end: string }`. When enabled, `computeTicketSla` and `slaAttainment` measure elapsed **business** minutes (only hours within the configured window on configured days) instead of wall-clock. SLA settings tab gains a "Business hours" section (enable toggle, timezone, weekdays, start/end). Wall-clock remains the default.

### C4. Better automation
`AutomationRule` becomes multi-condition:
```ts
interface AutomationRule {
  id: string; name: string; enabled: boolean;
  match: 'all' | 'any';                 // combine conditions
  conditions: { type: AutomationConditionType; value: string }[];
  actions: { type: AutomationActionType; value: string }[]; // multiple actions
  runOn: 'create' | 'create_update';
}
```
New condition types: `channel_is`, `from_contains`. New action types: `set_status`, `assign_round_robin`. The automation engine evaluates `match` over `conditions` and applies all `actions`; `runOn: create_update` also fires on ticket PATCH. The Automation settings editor gains add/remove condition + action rows, the all/any toggle, and the run-on selector. A **migration** upgrades existing single-condition rules to the new shape.

## Architecture, data flow, testing

- **Server:** new tables `ai_agents`, `ai_actions`, `channels`; columns `tickets.channelId`, `agents.status`/`inviteToken`/`signature`; migrations for each; `app_settings` keys `sla_hours` and the upgraded `automation`. New modules: `ai-run.ts` (runAgents/deflect wrappers over the shared engine logic), `channels.ts` (inbound/thread), plus routes in `api.ts`. Keep `api.ts` from ballooning by splitting route groups into `api/ai.ts`, `api/channels.ts` if it grows unwieldy.
- **Shared engine logic** lives in one place and is mirrored to the web `LocalRepository` for demo/test parity (same pattern as `deal-stats.ts`/`sla.ts`).
- **Web:** types mirrored; `LocalRepository` implements every new method + backfills v0.4 fields for old blobs; Zustand store slices (`aiAgents`, `aiActions`, `channels`) with optimistic mutations + rollback; hooks for the queues/fleet stats.
- **UI:** new feature dirs `features/agents/` (or extend `features/ai/`), `features/channels/`; settings tabs Team + upgraded SLA/Automation/Profile; new rail icon for Channels; `web/public/widget.html`.
- **Tests (Vitest):** engine `deflect`/`runAgent` decisions; server agent-run on create + approve/dismiss; channel inbound (token gate, contact upsert, ticket creation) + thread; business-hours SLA math; multi-condition automation (all/any, multi-action, run-on-update); team invite create/role/remove. Type-gate strict both workspaces.
- **Verification:** browser pass over AI Agents (overview/drafts/resolved/editor), Channels (directory + live widget), Settings (team/profile/SLA/automation) in light + dark; the widget exercised end-to-end (open conversation → agent reply appears).

## Success criteria
- An AI agent set to Resolve auto-answers a KB-matching ticket and it appears in "Resolved by AI"; a Draft-level agent fills the Drafts queue; approving a draft sends it.
- A message POSTed to a channel's inbound webhook (and one sent through the live web widget) both create real tickets that show their source; the widget shows the agent's reply.
- Team invites create members with shareable links; profile signature flows into drafts; business-hours SLA changes the clock; a multi-condition automation rule fires.
- Strict TS clean, all tests green, `docker build` still works, pushed to GitHub with readable history.
